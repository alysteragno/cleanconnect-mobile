Revise and properly finish a feature that was drafted from the cleanconnect-web side (cross-repo edit, not tested in a real Expo/RN environment): letting a customer pin their exact GPS location on an EXISTING booking that was created without one, and reviewing whether the draft handles all the edge cases a mobile-native session would catch.

CONTEXT — why this exists

On the web admin side, the "New Booking" form (phone-in/walk-in bookings created by staff on a customer's behalf) no longer has a map/pin picker — it was removed as redundant next to the structured address fields (unit/street/barangay/city/province). That means bookings created this way now have `service_lat` / `service_lng` = null.

Those columns are NOT cosmetic on your side:
- `app/(cleaner)/jobs/[id].tsx:581-587, 846-853` — the cleaner's job detail screen only shows a map pin + "Get Directions" button when `service_lat`/`service_lng` are present. Null = no pin, no directions, cleaner just sees the raw text address.
- `app/(cleaner)/jobs/[id].tsx:283-290` — the "I've arrived" flow does a haversine geofence check against `service_lat`/`service_lng` before letting the cleaner proceed. If null, that guard is silently skipped — no arrival validation happens at all.
- `lib/ai-assignment.ts` (web side) uses it as a proximity-scoring fallback for AI dispatch.

So for bookings created without a pin, the plan is: prompt the customer (who has an account/app, unlike a brand-new walk-in customer who hasn't set a password yet) to open the booking in the app and pin their location themselves — their device GPS is far more accurate than geocoding a typed address anyway.
