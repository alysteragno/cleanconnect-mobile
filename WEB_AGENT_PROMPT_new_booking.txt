## Fields the mobile customer booking form writes to `bookings` (match this shape for the admin-created booking insert)

- `service_id` (FK to services.id) / service slug reference
- `space_type` — 'residential' | 'condo' | 'office' | null (only for the 5 sqm-priced services above; null otherwise)
- `property_sqm` — numeric, only when space_type applies; null otherwise
- `sofa_seaters` — numeric, only set when service is sofa_couch_deep_cleaning and > 0; null otherwise
- `service_date`, `service_time`
- `service_lat`, `service_lng` — GPS coords of the service address (customer pins on a map in-app). Feeds the AI dispatch/matching engine, so the web form needs an equivalent way to capture or manually enter lat/lng (e.g. an address geocode lookup or a pin-on-map component) — do not leave this null if avoidable.
- `service_address_label`, plus address breakdown fields (unit, street, barangay, city, province) — check exact column names in the bookings table schema before writing the insert.
- `payment_method` — 'cash' | 'gcash' | 'maya' | 'bank_transfer' | 'bank_check'
- `payment_reference`, `payment_proof_uri` — required for gcash/maya/bank_transfer, not for cash
- `furniture_images` (string[] of Storage URLs), `furniture_videos` (string[] of Storage URLs, optional), `other_furniture` (free text), `special_notes` (free text) — likely less relevant for an admin-entered booking but keep the columns nullable/optional in the form
- `payment_status` — mobile now labels this contextually: 'paid' / 'partial' / 'refunded' show as-is; for 'pending', cash bookings show "Awaiting Payment" while digital methods show "Pending Confirmation" (since digital ones need admin verification of a reference/proof, cash is just collected on-site). Apply the same logic to any admin-facing status display for consistency.
